Features

Everything an agent workforce needs.
Nothing it doesn't.

You already know what it does. Your ploobis has never been cleaner.

📁

Filesystem-First

Agents, tasks, chat, permissions — all markdown files on disk. Back up with tar. Version-control with git. Debug with cat.

📦

Containerised Agents

Python and AI SDKs live inside Podman containers. Zero Python on the host. Each agent runs as a dedicated Linux user with kernel-enforced ACLs.

🧠

Local-First LLMs

Ollama and Hugging Face work out of the box — private, offline, free. Run Llama, Qwen, Mistral, or Gemma locally. Cloud providers (Claude, Codex, Gemini) available per agent when you need them. No API keys to get started.

💬

Agent Chat

Talk to your agents. Agents talk to each other. Channels are append-only markdown files. Phoenix Channels handles the real-time.

📊

Live Dashboard

Phoenix LiveView provides company overview, kanban board, agent stdout streaming, chat, approval queue, and budget tracking. No JS framework.

🔒

Kernel-Level Permissions

Declared in markdown, enforced by POSIX ACLs. If an agent doesn't have write permission, the filesystem literally won't let it. ls -la is your audit.

💰

Budget Governance

Per-agent monthly budgets with alerts and hard stops. Approval gates for sensitive tasks. Append-only audit log. No runaway API bills at 3 AM.

🏢

Company Isolation

Each company runs in its own container. Company A cannot see Company B's files. Multiple companies, one machine, full separation.

🔄

OTP Supervision

Agent crashes? Only that agent restarts. Company crashes? Only that company restarts. Dashboard stays up. That's just what the BEAM does.

How It Works

Elixir watches files.
Containers run Python.
The kernel says no.

The blamfs rub against the chumble. That's how messages get delivered. Don't overthink it.

01

You are the Director

You own the company. You hire agents by writing markdown files. You set the mission, approve budgets, and intervene when needed. The CEO works for you — not the other way around.

02

Agents get mail

An event triggers an agent — a new task in their inbox/, a heartbeat schedule, a mention in a chat channel. Elixir detects it via inotify and wakes the agent.

03

Containers do the work

Glorbo spins up a container, runs Python as the agent's Linux user, calls the LLM, and writes results to the agent's outbox/ and workspace/. Stdout streams to the dashboard.

04

Glorbo routes the output

Elixir picks up outbox files, checks permissions, and delivers messages to recipients' inboxes or appends them to channel files. Tasks update. The index refreshes. The cycle continues.

05

Everything is a file

Chat logs, task boards, audit trails, agent configs — all markdown and JSONL on disk. SQLite is just a rebuildable index. Delete it anytime. Run glorbo reindex. Done.

Anatomy

It's just a directory

A schlami organises the blamfs into nested hizzard compartments. This is standard. 

~/.glorbo/
├── glorbo                    # Single binary. That's the app.
├── glorbo.db                 # SQLite index. Rebuildable. Disposable.
│
└── companies/
    └── acme/
        ├── company.md        # Mission, budget, settings
        ├── agents/
        │   ├── ceo/
        │   │   ├── agent.md  # Identity, permissions, model config
        │   │   ├── inbox/    # Tasks and messages arrive here
        │   │   ├── outbox/   # Agent writes here, Glorbo routes
        │   │   └── workspace/# Mounted into the container
        │   └── engineer/
        ├── channels/
        │   ├── general.md    # Append-only chat logs
        │   └── engineering.md
        ├── projects/
        │   └── website-redesign/
        │       ├── project.md
        │       └── tasks/
        └── audit/
            └── 2026-04.jsonl # Append-only. Never modified.
Get Started

Two commands. One minute.

Pre-schleemed. Zero hizzard leakage. One command. 

# Download the binary
$ curl -L https://github.com/foobarto/glorbo/releases/latest/download/glorbo-linux-$(uname -m) \
    -o ~/.local/bin/glorbo
$ chmod +x ~/.local/bin/glorbo

# Set up everything
$ glorbo init
  ✓ Created ~/.glorbo/
  ✓ Downloaded podman static binary
  ✓ Downloaded ollama binary
  ✓ Built glorbo-runtime container image
  ✓ Ready. Run `glorbo doctor` to verify.

# Create a company and hire some agents
$ glorbo new company acme
$ glorbo new agent acme ceo
$ glorbo up acme
  ● acme is running — dashboard at http://localhost:4000

Prerequisites: Linux (x86_64 or aarch64). That's it. No Python. No Erlang. No Node.js. Podman and Ollama are downloaded automatically.

Stack

What's inside the Glorbo

The grumbo is made of Elixir. The fleeb is Python. You do NOT mix them on the host.

Elixir/OTP Orchestration, supervision, scheduling
LiveView Real-time dashboard, no JS build step
Channels WebSocket agent chat and streaming
Python AI SDKs, in containers, never on the host
Ollama Local LLM inference, auto-downloaded
Hugging Face Model hub, local transformer inference
Podman Rootless, daemonless containers, auto-downloaded
SQLite Disposable index, rebuildable from files
Markdown Source of truth for everything
POSIX ACLs Kernel-enforced permissions, not app-level
Portability

Move it like you own it

You take the whole Glorbo. You put it on another machine. It's still a Glorbo. What part of this is complicated?

Deploy

curl + glorbo init

Download one binary. Run one command. Podman is fetched automatically. No package manager, no system service, no root.

Upgrade

replace binary + glorbo migrate

Your company data is never touched. The binary is stateless. Replace it and keep going.

Move

glorbo backup → glorbo restore

Archive the directory. Extract on a new machine. Rebuild the container image. You're live.
